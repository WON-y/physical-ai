# PPE 착용 점검 로봇 — SBC 내부 구조 및 SBC·MCU 선정 보고서

> 대상: Raspberry Pi 5 + AI HAT+ (26 TOPS), RoboClaw 2×15A
> 실행 환경: Docker Compose, ROS 2
> 구성: 1부 SBC 내부 소프트웨어 구조 (컨테이너 관계도) / 2부 SBC · MCU 선정

---

## 1부. SBC 내부 소프트웨어 구조 (컨테이너 관계도)

### 1. 설계 방향

라즈베리파이 안의 소프트웨어를 **역할에 따라 5개 컨테이너**로 나눈다. 나누는 기준은 다음과 같다.

- **장애 격리**: 한 컨테이너에서 오류가 나도 다른 기능은 계속 동작해야 한다. 특히 비전 판별에서 오류가 나도 주행 안전에는 영향이 없어야 한다.
- **독립 배포**: AI 모델을 재학습하면 비전 판별 컨테이너만 교체한다.
- **장치 접근 분리**: 하드웨어를 직접 다루는 코드는 해당 장치가 필요한 컨테이너에만 둔다.
- **통신 경계 구분**: 로봇 내부는 **ROS 2 토픽**, 로봇 외부(서버)는 **MQTT**로 통신한다.

### 2. 컨테이너 관계도

```text
                                    서버 (MQTT 브로커 · 대시보드 · 알림)
                                        ▲
                                        │ Wi-Fi · MQTT over TLS (브리지 연결)
 ═══════════════ Raspberry Pi 5 (Docker) ═╪══════════════════════════════════════
                                        │
                              ⑤ MQTT 브로커 (Mosquitto)
                                        ▲
                                        │ MQTT (로봇 내부, localhost)
                                        │
                              ④ 이벤트 관리 (SQLite · 증빙 사진)
                               ▲                 ▲
             /ppe/violation    │                 │  /amcl_pose (②에서)
             (이벤트 + 사진)   │                 │  /battery · /estop (①에서)
                               │                 │
       ③ 비전 판별 ────────────┘                 │
       (YOLO · 추적 · 착용 판정)                 │
            │   ▲                                │
  /ppe/     │   │ /patrol/state                  │
  violation ▼   │ (순찰 상태)                    │
       ② 자율주행 ───────────────────────────────┤
       (위치 추정 · Nav2 · 순찰 관리)            │
            │   ▲                                │
   /cmd_vel ▼   │ /scan · /odom · /battery · /estop
       ① 하드웨어 드라이버 ──────────────────────┘
       (모터 · LiDAR · E-Stop · 안전 감시)
 ═══════════════════════════════════════════════════════════════════════════════
 하드웨어   카메라 ─CSI─▶ ③     AI HAT+ ◀─PCIe─▶ ③
            LiDAR ─USB─▶ ①     모터 컨트롤러 ◀─USB─▶ ①     E-Stop ─GPIO─▶ ①
```

- 실선 화살표는 **데이터가 흐르는 방향**이다.
- ①~④ 컨테이너끼리는 ROS 2 토픽으로, ④→⑤→서버는 MQTT로 통신한다.

### 3. 컨테이너별 역할

#### ① 하드웨어 드라이버

로봇의 **물리 장치를 직접 다루는 유일한 컨테이너**다.

- **모터 제어**: 자율주행에서 받은 속도 명령(`/cmd_vel`)을 RoboClaw 명령으로 바꿔 USB로 보낸다. 엔코더 값을 읽어 주행 거리(`/odom`)를 계산한다.
- **LiDAR 수신**: 360° 거리 데이터를 받아 `/scan` 토픽으로 내보낸다.
- **E-Stop 감지**: GPIO로 비상정지 버튼 상태를 읽어 `/estop`으로 알린다. (실제 모터 전원 차단은 하드웨어 컨택터가 담당)
- **배터리 상태**: RoboClaw에서 읽은 배터리 전압을 `/battery`로 내보낸다.
- **안전 감시**: 속도 명령이 **0.5초 이상 오지 않으면 모터를 정지**시킨다. 자율주행 컨테이너가 멈춰도 로봇이 계속 달리는 일을 막는다.

#### ② 자율주행

로봇이 **어디로, 언제 움직일지** 결정한다.

- **위치 추정**: 미리 만든 지도와 LiDAR 데이터로 현재 위치를 계산한다(AMCL).
- **경로 계획**: Nav2로 다음 웨이포인트까지 경로를 만들고, 장애물을 피해 속도 명령을 보낸다.
- **순찰 관리**: 순찰 순서를 상태로 관리한다.

| 순찰 상태       | 동작                                              |
| --------------- | ------------------------------------------------- |
| 이동 (PATROL)   | 다음 웨이포인트로 이동                            |
| 스캔 (SCANNING) | 웨이포인트에서 정지 후 제자리 회전하며 촬영       |
| 대기 (HOLD)     | 미착용 감지 시 정지, 30초 후 재확인 결과를 기다림 |
| 복귀 (RETURN)   | 배터리가 부족하면 출발 지점으로 이동              |
| 정지 (STOPPED)  | E-Stop이 눌리면 모든 동작 중단                    |

- 현재 순찰 상태를 `/patrol/state`로 비전 판별에 알린다.

#### ③ 비전 판별

카메라 영상으로 **작업자의 보호구 착용 여부를 판정**한다.

- **영상 입력**: 카메라에서 프레임을 받아 640×640으로 줄인다.
- **객체 검출**: AI HAT+에서 YOLO를 실행해 person·helmet·vest·head를 검출한다.
- **추적**: ByteTrack으로 작업자마다 추적 ID를 붙인다.
- **착용 판정**: 포함률 규칙으로 판정하고, 애매한 경우에만 MediaPipe Pose로 다시 확인한다.
- **이벤트 확정**: 같은 추적 ID에서 미착용이 **연속 5프레임** 이어지면 `/ppe/violation`을 보낸다. (사진, 박스 좌표, 유형, 신뢰도 포함)
- **부하 조절**: `/patrol/state`를 보고 이동 중에는 5 FPS, 스캔 중에는 15 FPS로 검출 빈도를 바꿔 CPU를 아낀다.

#### ④ 이벤트 관리

미착용 이벤트를 **기록하고 서버로 보낼 메시지를 만든다**.

- **이벤트 정리**: 비전 판별에서 받은 이벤트에 위치(`/amcl_pose`)와 시각을 붙인다.
- **개인정보 처리**: 증빙 사진에서 head·person 박스 위치를 이용해 얼굴을 블러 처리한다.
- **중복 억제**: 같은 위치에서 같은 작업자 알림은 10분간 다시 보내지 않는다.
- **로컬 저장**: 이벤트는 SQLite, 사진은 microSD에 저장한다. 서버 전송 여부도 함께 기록한다.
- **상태 보고**: 로봇 상태(위치, 배터리, 순찰 상태, E-Stop)를 5초마다 MQTT로 보낸다.

#### ⑤ MQTT 브로커

로봇과 서버 사이의 **통신 창구**다.

- 로봇 안에 Mosquitto 브로커를 두고, 서버 브로커와 **브리지**로 연결한다.
- Wi-Fi가 끊기면 보낼 메시지를 **디스크에 보관**하고, 연결이 복구되면 자동으로 다시 보낸다.
- 서버와의 통신은 **TLS로 암호화**한다.
- 다른 컨테이너는 서버 주소를 몰라도 되고, 로컬 브로커에만 메시지를 보내면 된다.

### 4. 컨테이너 간 통신

#### 4.1 ROS 2 토픽 (로봇 내부)

| 토픽               | 보내는 쪽 → 받는 쪽 | 내용                                              | 주기           |
| ------------------ | -------------------- | ------------------------------------------------- | -------------- |
| `/scan`          | ① → ②             | LiDAR 거리 데이터                                 | 10Hz           |
| `/odom`          | ① → ②             | 엔코더 기반 주행 거리                             | 20Hz           |
| `/battery`       | ① → ②, ④         | 배터리 전압·잔량                                 | 1Hz            |
| `/estop`         | ① → ②, ④         | 비상정지 상태                                     | 상태가 바뀔 때 |
| `/cmd_vel`       | ② → ①             | 직진·회전 속도 명령                              | 10~20Hz        |
| `/amcl_pose`     | ② → ④             | 지도상 로봇 위치                                  | 위치가 바뀔 때 |
| `/patrol/state`  | ② → ③             | 현재 순찰 상태                                    | 상태가 바뀔 때 |
| `/ppe/violation` | ③ → ②, ④         | 미착용 이벤트 (유형, 신뢰도, 추적 ID, 사진, 박스) | 이벤트 발생 시 |
| `/ppe/recheck`   | ③ → ②, ④         | 30초 후 재확인 결과 (착용 확인 / 미개선)          | 재확인 시      |

#### 4.2 MQTT 토픽 (로봇 ↔ 서버)

| 토픽                     | 방향         | 내용                              | QoS                      |
| ------------------------ | ------------ | --------------------------------- | ------------------------ |
| `ppe/{로봇ID}/event`   | 로봇 → 서버 | 미착용 이벤트, 증빙 사진          | 1 (반드시 1회 이상 전달) |
| `ppe/{로봇ID}/recheck` | 로봇 → 서버 | 재확인 결과                       | 1                        |
| `ppe/{로봇ID}/status`  | 로봇 → 서버 | 위치, 배터리, 순찰 상태           | 0 (최신 값만 중요)       |
| `ppe/{로봇ID}/command` | 서버 → 로봇 | 순찰 시작·중지, 점검 시간대 변경 | 1                        |

> QoS 1: 받는 쪽이 확인할 때까지 다시 보내므로 이벤트가 사라지지 않는다.
> QoS 0: 한 번만 보내며, 상태 정보처럼 곧 새 값이 오는 데이터에 쓴다.

### 5. 동작 흐름

#### 5.1 미착용 감지부터 알림까지

1. ② 자율주행이 웨이포인트에 도착해 상태를 **스캔**으로 바꾸고 `/patrol/state`로 알린다.
2. ③ 비전 판별이 검출 빈도를 15 FPS로 올리고 작업자를 검출·추적한다.
3. 미착용이 연속 5프레임 이어지면 ③이 `/ppe/violation`을 보낸다.
4. ② 자율주행은 이를 받고 로봇을 **정지(대기)** 상태로 둔다.
5. ④ 이벤트 관리는 위치를 붙이고, 얼굴을 블러 처리하고, SQLite에 저장한 뒤 MQTT로 보낸다.
6. ⑤ MQTT 브로커가 서버로 전달하고, 서버가 관리자에게 알림을 보낸다.
7. 30초 후 ③이 다시 판정해 `/ppe/recheck`로 결과를 보낸다.
8. ②는 순찰을 재개하고, ④는 재확인 결과를 서버로 보낸다.

#### 5.2 Wi-Fi가 끊겼을 때

1. ⑤ MQTT 브로커가 서버 연결이 끊긴 것을 감지하고 메시지를 디스크에 보관한다.
2. 순찰과 판정은 로봇 안에서 이뤄지므로 **계속 진행**한다.
3. 연결이 복구되면 ⑤가 보관한 메시지를 순서대로 서버에 보낸다.
4. ④는 서버 수신이 확인되지 않은 이벤트를 SQLite에 "미전송"으로 표시해 두었다가 다시 보낸다. (2중 보관)

### 6. 장애 대응 (컨테이너가 멈췄을 때)

| 멈춘 컨테이너        | 영향                   | 대응                                                                                                          |
| -------------------- | ---------------------- | ------------------------------------------------------------------------------------------------------------- |
| ① 하드웨어 드라이버 | 모터 명령이 끊김       | RoboClaw의 **시리얼 타임아웃 설정**으로 명령이 끊기면 모터가 자동 정지. Docker가 컨테이너를 자동 재시작 |
| ② 자율주행          | 속도 명령이 끊김       | ①의 안전 감시가 0.5초 후 모터 정지. 재시작 후 마지막 위치에서 위치 추정 재개                                 |
| ③ 비전 판별         | 착용 판정 중단         | 순찰은 계속됨. ④가 "비전 중단" 상태를 서버에 보고. 자동 재시작                                               |
| ④ 이벤트 관리       | 이벤트 기록·전송 중단 | 자동 재시작. 서버는 상태 보고가 끊긴 것으로 이상을 감지                                                       |
| ⑤ MQTT 브로커       | 서버 전송 중단         | ④가 이벤트를 SQLite에 보관하고, 브로커 복구 후 다시 보냄                                                     |

→ 어떤 컨테이너가 멈춰도 **로봇이 제어 없이 움직이는 상황은 생기지 않는다.**

### 7. Docker 실행 설정

| 컨테이너             | 연결 장치                               | 저장 공간 (볼륨)              | CPU 배정                      | 재시작 정책 |
| -------------------- | --------------------------------------- | ----------------------------- | ----------------------------- | ----------- |
| ① 하드웨어 드라이버 | 모터 컨트롤러·LiDAR (USB 시리얼), GPIO | —                            | 코어 0~1 공유 (우선순위 높음) | 항상 재시작 |
| ② 자율주행          | —                                      | 지도, 웨이포인트, 마지막 위치 | 코어 0~1 공유 (우선순위 높음) | 항상 재시작 |
| ③ 비전 판별         | 카메라, AI HAT+                         | AI 모델 파일                  | 코어 2~3                      | 항상 재시작 |
| ④ 이벤트 관리       | —                                      | SQLite DB, 증빙 사진          | 남는 자원 사용                | 항상 재시작 |
| ⑤ MQTT 브로커       | —                                      | 미전송 메시지 보관            | 남는 자원 사용                | 항상 재시작 |

- **네트워크**: ①~④는 ROS 2 통신을 위해 **호스트 네트워크**를 같이 쓰고, 같은 ROS 도메인 ID를 사용한다.
- **CPU 배정**: 주행에 관련된 ①②를 코어 0~1에, 비전 판별을 코어 2~3에 나눠, AI 부하가 커져도 주행 제어가 늦어지지 않게 한다.
- **실행 순서**: ⑤ → ① → ② → ③ → ④ 순서로 시작한다.
- **모델 업데이트**: 새 YOLO 모델을 배포할 때는 ③ 컨테이너만 교체하고 다시 시작한다.

### 8. 1부 정리

- 기능을 **5개 컨테이너**로 나눠, 하나가 멈춰도 나머지가 계속 동작하도록 설계했다.
- **자율주행과 비전 판별을 분리**해서 AI 쪽 오류가 주행 안전에 영향을 주지 않게 했다.
- 로봇 내부는 **ROS 2 토픽**, 서버와는 **MQTT**로 통신 경계를 나눴다.
- 로컬 MQTT 브로커와 SQLite로 **2중 보관**을 해서, Wi-Fi가 끊겨도 이벤트가 사라지지 않는다.
- 하드웨어 드라이버의 안전 감시와 RoboClaw 타임아웃으로 **어떤 장애에서도 로봇이 멈추도록** 했다.

## 2부. SBC · MCU 선정

> 근거 자료: 8_5 피지컬 AI 부품 도감 (조건 조절기, 질문으로 고르기, 부품별 장단점)
> 결론: **SBC = Raspberry Pi 5 + AI HAT+ (26 TOPS)**, **MCU = RoboClaw 2×15A에 내장된 모터 제어 MCU**

### 1. 선정 기준: SBC와 MCU의 역할 분담

자료에서는 SBC를 **두뇌**, MCU를 **반사신경**으로 구분한다.

| 구분           | 특징                                                          | 이 제품에서 맡는 일                                               |
| -------------- | ------------------------------------------------------------- | ----------------------------------------------------------------- |
| SBC (두뇌)     | 리눅스·도커·AI 실행 가능, 부팅에 수십 초, OS가 멈출 수 있음 | 영상 인식, 착용 판정, 자율주행 경로 계획, 이벤트 저장, Wi-Fi 알림 |
| MCU (반사신경) | 켜자마자 동작, 정해진 시간 안에 반드시 반응                   | 모터 속도 제어(PID), 엔코더 읽기, 전류 제한, 명령이 끊기면 정지   |

리눅스는 업데이트나 메모리 부족으로 멈출 수 있으므로, **모터 제어와 안전 기능은 SBC가 아닌 MCU에 맡긴다.**

### 2. 제품 요구 조건

| 조건         | 값             | 근거                                                     |
| ------------ | -------------- | -------------------------------------------------------- |
| 리눅스·도커 | 필요           | 컨테이너 5개, ROS 2 실행                                 |
| 전원         | 상시 전원      | 매일 충전하는 770Wh 배터리. 저전력 장기 동작 장치가 아님 |
| AI 연산      | 보통           | 카메라 1대, YOLO(15 FPS) + MediaPipe(필요할 때만)        |
| 실시간 제어  | SBC에는 불필요 | 모터 제어는 RoboClaw, 비상정지는 하드웨어 컨택터가 담당  |
| 무선         | Wi-Fi          | 관리자 알림 전송                                         |

### 3. SBC 선정: Raspberry Pi 5 + AI HAT+ (26 TOPS)

#### 3.1 조건 조절기 결과

2장의 조건을 자료의 조건 조절기에 넣은 결과다.

| 순위 | 부품                     | 판정         | 비고                                                      |
| ---- | ------------------------ | ------------ | --------------------------------------------------------- |
| 1    | **Pi 5 + AI HAT+** | ✓ 조건 충족 | AI 성능이 요구치에 딱 맞고, 자료·생태계 점수가 가장 높음 |
| 2    | Jetson Orin Nano         | ✓ 조건 충족 | 요구치보다 성능이 높아 감점 (과한 사양)                   |
| 3    | RK3588 보드              | ✓ 조건 충족 | 자료·생태계 점수가 낮음                                  |
| 4    | Raspberry Pi 5 (단독)    | ✕ AI 부족   | NPU가 없음                                                |

#### 3.2 질문으로 고르기 결과

리눅스·AI 필요? **예** → AI 부하가 큰가? **아니오** (카메라 1대) → 특수 요구? **없음** → 공간·전력 제약? **아니오** → **Raspberry Pi 5**

질문 트리의 결과는 Pi 5지만, Pi 5 단독은 NPU가 없어 YOLO를 15 FPS로 돌리기 어렵다. 따라서 **Pi 5에 NPU를 더한 AI HAT+**를 최종 선택한다.

#### 3.3 선정 이유

| 장점 (자료 기준)   | 이 제품에서의 의미                                          |
| ------------------ | ----------------------------------------------------------- |
| 기존 Pi 그대로     | Pi 5의 풍부한 자료와 도구를 그대로 쓰면서 AI 속도만 올림    |
| 강한 NPU (26 TOPS) | YOLO 추론을 NPU가 전담해, CPU는 자율주행(Nav2)에 집중       |
| 만능 인터페이스    | CSI 카메라, PCIe(AI HAT+), USB(LiDAR·RoboClaw)를 모두 연결 |
| 리눅스·도커       | 1부의 컨테이너 5개 구조를 그대로 운영                       |

#### 3.4 다른 후보를 고르지 않은 이유

| 후보                  | 고르지 않은 이유                                                                                              |
| --------------------- | ------------------------------------------------------------------------------------------------------------- |
| Jetson Orin Nano      | 비전 AI 성능은 가장 강하지만 가격이 Pi 5의 몇 배이고 전력이 7~25W. 카메라 1대에는 과한 사양                   |
| RK3588 보드           | 가성비는 좋지만 자료가 부족하고 RKNN 모델 변환이 필요. 개인 프로젝트에서 문제 해결에 시간이 오래 걸릴 수 있음 |
| Raspberry Pi 5 (단독) | NPU가 없어 AI를 CPU로 돌려야 하는데, CPU는 이미 자율주행에 쓰이고 있음                                        |
| Pi Zero 2 W           | RAM 512MB라 컨테이너 여러 개와 AI 모델을 올릴 수 없음                                                         |
| AI HAT+ 2 (40 TOPS)   | 8GB RAM은 LLM 실행용이라 이 제품에는 불필요. 비전 추론은 26 TOPS로 충분                                       |

#### 3.5 사양

| 항목      | 내용                                                                     |
| --------- | ------------------------------------------------------------------------ |
| SBC       | Raspberry Pi 5 (8GB), Cortex-A76 4코어 2.4GHz                            |
| AI 가속기 | AI HAT+ 26 TOPS (Hailo-8), PCIe Gen 3 연결                               |
| 전원      | 5V, 평균 약 2.6A / 피크 약 4.7A (AI HAT+·카메라·LiDAR 포함)            |
| 연결 장치 | 카메라(CSI), AI HAT+(PCIe), LiDAR(USB), RoboClaw(USB), E-Stop 감지(GPIO) |
| 무선      | 내장 Wi-Fi 5 (MQTT over TLS)                                             |
| 냉각      | 액티브 쿨러 필수 (80°C 이상에서 성능 저하)                              |

### 4. MCU 선정: RoboClaw 2×15A (내장 MCU)

#### 4.1 별도 MCU를 두지 않는 이유

자료의 질문 트리로 MCU를 고르면 다음과 같다.

리눅스·AI 필요? **아니오** → 무선 필요? **아니오** (Wi-Fi는 Pi가 담당) → 모터를 정밀하게 제어하나? **예** → **STM32**

이 제품에서 MCU에 필요한 일은 **모터 정밀 제어**와 **안전 정지**다. RoboClaw는 **모터 제어 전용 MCU가 내장된 모터 컨트롤러**로, STM32에 펌웨어를 직접 작성해서 해야 할 일을 이미 기능으로 갖추고 있다. 따라서 별도 MCU 없이 **RoboClaw의 내장 MCU가 반사신경 역할**을 맡는다.

| MCU에 필요한 기능 | STM32로 할 경우                      | RoboClaw                                         |
| ----------------- | ------------------------------------ | ------------------------------------------------ |
| 엔코더 읽기       | 타이머 엔코더 모드 설정, 펌웨어 작성 | 직교 엔코더 입력 2채널 내장                      |
| 속도 PID 제어     | PID 코드 작성·튜닝                  | 내장 (게인 값만 설정)                            |
| 모터 구동         | 별도 모터 드라이버 필요              | 2채널 드라이버 내장 (채널당 연속 15A / 피크 30A) |
| 전류 제한         | 전류 센서 + 코드 작성                | 채널별 최대 전류 설정                            |
| 가속 제한         | 코드 작성                            | 가속도 값 설정                                   |
| 명령 끊김 시 정지 | 워치독 코드 작성                     | 시리얼 타임아웃 설정                             |
| 배터리 전압 측정  | ADC + 분압 회로                      | 내장 (Pi에서 읽기 가능)                          |

#### 4.2 선정 이유

- **안전 기능을 SBC에서 분리**: Pi가 멈추거나 재부팅되어도 RoboClaw가 시리얼 타임아웃으로 모터를 스스로 멈춘다.
- **개발 기간 단축**: 펌웨어를 직접 짜지 않고 설정값만 조정하면 되므로, AI와 자율주행 개발에 시간을 집중할 수 있다.
- **검증된 제품**: 모터 제어 전용 제품이라 직접 만든 펌웨어보다 안정적이다.
- **부품 수 감소**: MCU 보드와 모터 드라이버를 따로 사지 않아 배선이 단순해진다.

#### 4.3 감수하는 점

| 단점                         | 대응                                                                          |
| ---------------------------- | ----------------------------------------------------------------------------- |
| 가격이 높음 (약 20만 원)     | MCU + 모터 드라이버 2개 + 개발 시간을 합치면 큰 차이가 아님                   |
| 내부 펌웨어를 수정할 수 없음 | 필요한 기능(PID, 전류 제한, 타임아웃)이 모두 설정으로 제공됨                  |
| 채널이 2개뿐                 | 4륜 스키드 스티어 방식으로 왼쪽 모터 2개를 채널 1, 오른쪽 2개를 채널 2에 연결 |
| E-Stop을 직접 처리하지 않음  | E-Stop은 하드웨어 컨택터가 모터 전원을 차단하고, Pi는 GPIO로 상태만 감지      |

#### 4.4 사양과 설정값

| 항목                            | 내용                                                |
| ------------------------------- | --------------------------------------------------- |
| 모델                            | Basicmicro RoboClaw 2×15A                          |
| 입력 전압                       | 6~34V (24V 배터리 사용)                             |
| 출력 전류                       | 채널당 연속 15A / 피크 30A                          |
| 통신                            | USB (Packet Serial) → Pi 5                         |
| 엔코더 입력                     | 직교 엔코더 2채널 (5V)                              |
| **채널당 최대 전류 설정** | 25A (모터 2개 구속 시 40A로 피크 30A를 넘지 않도록) |
| **시리얼 타임아웃 설정**  | 0.5초 (Pi 명령이 끊기면 정지)                       |
| **가속 제한 설정**        | 0.5 m/s² 상당 (출발 시 돌입 전류 억제)             |

### 5. 최종 구성과 역할 분담

```text
            [ 두뇌 : SBC ]                              [ 반사신경 : MCU ]

  카메라 ─CSI─▶ Raspberry Pi 5 ──USB (Packet Serial)──▶ RoboClaw 2×15A
  LiDAR ──USB─▶  + AI HAT+    ◀── 엔코더 값·전류·전압 ──   (내장 MCU)
                    │   ▲                                   │   ▲
              Wi-Fi │   │ GPIO                     PWM 전력 │   │ 엔코더
                    ▼   │                                   ▼   │
               관리자 알림  E-Stop ──컨택터 차단──▶  DC 기어드 모터 ×4
```

| 상황        | SBC (Pi 5 + AI HAT+)                 | MCU (RoboClaw)                           |
| ----------- | ------------------------------------ | ---------------------------------------- |
| 평상시 순찰 | 경로 계산, 속도 명령 전송, 영상 인식 | 속도 명령대로 PID 제어                   |
| 미착용 감지 | 정지 명령, 이벤트 생성, Wi-Fi 알림   | 감속 후 정지                             |
| 바퀴가 걸림 | 전류 값을 읽고 경로 재계산           | 전류를 25A로 제한해 모터·드라이버 보호  |
| Pi가 멈춤   | (동작 불가)                          | 0.5초 후 시리얼 타임아웃으로 스스로 정지 |
| E-Stop 누름 | GPIO로 감지해 기록                   | 컨택터가 전원을 끊어 즉시 정지           |

### 6. 2부 정리

- **SBC는 Raspberry Pi 5 + AI HAT+ (26 TOPS)**: 자료의 조건 조절기에서 1순위로, AI 성능이 요구치에 맞고 자료가 가장 풍부하다.
- **MCU는 RoboClaw의 내장 MCU**: 자료의 질문 트리에서 나온 "모터 정밀 제어용 MCU" 역할을 RoboClaw가 기능으로 제공하므로 별도 MCU를 두지 않는다.
- **두뇌와 반사신경을 분리**해서, 리눅스가 멈춰도 모터는 안전하게 멈추도록 설계했다.
- 앞으로 확장할 때 **카메라를 여러 대로 늘리면 Jetson Orin Nano**, **모터 제어를 직접 구현하고 싶으면 STM32**로 바꿀 수 있다.
